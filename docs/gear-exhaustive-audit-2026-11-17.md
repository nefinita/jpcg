# 配装穷举流程审查（2026-11-17）

审查范围：候选空间、约束剪枝、合成、时间轴、CPU/AVX-512/wgpu MC、排序/Pareto、静态/动态桌面入口、取消与进度。当前真实配置的完整测试继续运行；本次未替换正在执行的二进制，未在计时机器上追加计算引擎/GPU复现负载。以下区分源码确认、轻量数值验证、硬件观察和待补回归。

## 正确性问题

### P1：跨门派装备被排除，完整遍历仍然可能漏解

位置：`crates/jpcg_gear/src/optimize.rs:26`、`:134`；对照 `examples/jpcg_app/src/components/GearPanel.tsx:128` 和 `data/gear/templates.toml:808`。

- UI 支持本门派装备和 `cross_school=true` 的外门派装备；合成器也按 `choice.school` 查模板，并正确排除外门派套装件数。
- 候选生成只保留 `t.school == req.loadout.school`，锁定/禁用校验也只查本门派模板。实际的冰心头部与护手不会进入莫问穷举；锁定它们会被拒绝。
- 当前“31.85亿原始组合、3.95亿合格组合”仅覆盖本门派模板。四件竞技场防具允许第五个防具用外门派，故这不是必然被四件套限制排除的无关选项。
- 应共用 UI/合成器的模板可穿规则并规范化 `Choice.school`，再按实际装备门派计算套装。修复后必须重新计算空间和重跑全量，旧测试只能用于旧空间的后端一致性。

### P1：动态桌面入口仍执行旧版有界搜索

位置：`examples/jpcg_app/src-tauri/src/commands/gear.rs:111` → `crates/jpcg_gear/src/host.rs:53`。

- static 调用 `optimize_joint`；dynamic 经 FFI 的 `optimize` 方法实际调用 `optimize`，最多一百万叶子且装饰轴包含“无”。
- `compute` 后端参数在旧路径不参与 MC 设备选择；dynamic 的取消函数也没有实际实现。
- 结果：同一 UI 操作在两个构建模式下搜索空间、预算、GPU使用和取消语义不同。
- 应为动态 ABI 暴露联合搜索、进度和取消状态，不能仅改一个函数名而留下无法取消的长调用。

### P1：四件套 CD 没有进入时间轴，联合搜索还丢失顶层警告

位置：`crates/jpcg_gear/src/catalog.rs:395`、`:410`；`crates/jpcg_gear/src/optimize.rs:696`、`:927`、`:995`；`crates/jpcg_combo/src/timeline_host.rs:339`。

- 合成器产生 `composed.cooldowns`，但 Timeline 分数和批量模板只替换 player，没有应用 cooldowns。
- 连招旧目标会显式拒绝未应用 CD；Timeline 目标没有相同保护。联合搜索的顶层 `warnings` 初始化为空后直接返回，丢失“4件套CD未应用”的提示（嵌套 Composed 仍保留）。
- 当前莫问竞技场四件套减少“孤影化双”CD 15秒；本轮连招没有该技能，因此未发现它直接改变本轮输出。但包含重复孤影/笑傲等 CD 相关排轴时会影响结果。
- 应先落实装备 CD 的统一时序适配，并让基线、逐候选和批量模板共用；完成前至少明确返回警告或拒绝不支持的目标。

### P2：GPU 大批次切片没有候选偏移

位置：`crates/jpcg_compute/src/lib.rs:160`、`:369`。

- host 的 while 递增 start，但 shader 始终 `cand = wid.x`，没有 start 参数，绑定缓冲区也未偏移。
- 65,536 个候选时，第二次 dispatch 重复候选 0，候选 65,535 没有被计算；重复区域还共享 atomicStore/atomicAdd 输出。
- 已用轻量下标推演确认遗漏；尚未在当前硬件计时期间启动 GPU 复现。
- 当前生产批次 32,768 不触发，所以这轮测试不受这一边界影响；公开 run API 及将来调大批次会触发。
- 应给 shader 明确 candidate base，或由外层按合法大小分批并分别绑定/收集。还应按设备存储缓冲区限制控制批次。

### P2：把总伤加进概率可能让较低击杀率胜出

位置：`crates/jpcg_gear/src/optimize.rs:703`、`:960`。

- 当前 score 为 `kills / samples + total_damage * 1e-12`。所谓“远小于一个样本分辨率”没有总伤上限保证。
- 50,000 样本下：25,000 次击杀、30,000,000 总伤的分数是 0.500030；25,001 次击杀、1,000,000 总伤的分数是 0.500021，反而输掉。
- 应按 `(kill_count, total_damage)` 做词典序比较，概率仍独立输出。Pareto 比较也必须按同一目标优先级处理。
- 本轮短窗口伤害规模远小于该示例，没有证据显示已经触发排序反转。

### P2：取消与进度有失真路径

位置：`crates/jpcg_gear/src/optimize.rs:828`；`examples/jpcg_app/src-tauri/src/commands/gear.rs:72`、`:96`；`crates/jpcg_gear/src/bin/gear-opt.rs:35`。

- UI 先注册进度对象，prepare/基线期间用户已可取消；随后 optimize_joint 把 cancel 重置为 false，可能吞掉早期取消。
- CLI 的 ctrlc_cancel 只做了空引用，没有注册 SIGINT 回调，Ctrl-C 无法按注释所说返回部分结果。
- Tauri monitor 无论成功、取消、报错最终都 emit 100，且 evaluated 在 GPU 完成前增加，不是严格已完成 MC 数。
- 长任务没有候选结果检查点，强制停止后丢失已完成的最佳/Pareto。已有旧并发测试的退出码 -15 是人为停止，不能作为算法失败统计。

### P2：GPU 长时间轴不支持超过64个伤害事件

位置：`crates/jpcg_compute/src/lib.rs:255`；请求动作上限见 `crates/jpcg_gear/src/optimize.rs:617`。

- 请求允许最多256个动作，CPU MC 接收任意长度事件；GPU固定 MAX_EVENTS=64，超过后直接错误返回。一次动作可能产生多个引导/DOT事件。
- 当前短连招没有发现触发；应在准备阶段明确验证支持范围，或用动态步长/压缩事件缓冲区支持长轴。按事件数简单拆成多个独立 MC 会破坏 HP/随机流连续性，不能作为等价修复。

### P2：AVX-512 检测条件弱于声明的指令要求

位置：`crates/jpcg_combo/src/kill_mc.rs:70`、`:185`。

- 函数声明需要 avx512f/dq/vl/bw，调用端只检测 avx512f。
- 仅支持子集的 CPU 不满足 target_feature 契约，可能非法指令。
- 当前9970X具备全部所需标志，不影响本轮；应匹配完整检测条件或收窄实际要求。

## 已确认的性能浪费

### 1. 优先级最高：完全相同的进攻面板重复模拟

位置：`crates/jpcg_gear/src/optimize.rs:900-971`。

- 击杀率联合分支没有缓存/去重，每个合法组合重新合成、simulate、MC。其他优化分支至少有一个按完整 stats 的缓存，但即使按完整 stats 缓存仍区分了只改生存属性的方案。
- 当前数据中上衣3、腰带3、项链2、腰坠2种附魔均只改变体质/御劲/化劲。莫问规则中体质只换气血；这些字段不进入战斗 player。3×3×2×2=36个组合的进攻输入完全相同，加速也相同。
- 因而本轮3.950208亿个合法组合，仅这四个槽的重复因子就为36。进攻输入的组合数上界可降至10,972,800；其余无关门派五维附魔还存在额外重复。
- 正确做法是按真正的进攻玩家参数及会影响时序的装备效果分组，复用确定性时间轴及MC；防御面板和配装仍分别用于约束、最佳配装选择和生存Pareto。不能直接丢弃36种方案。
- 这是评分次数的去重上界分析，不等于端到端已实测36倍加速。缓存还要控制内存，最好调整遍历顺序，使同组方案相邻并复用。

### 2. CPU准备与GPU计算没有重叠

位置：`crates/jpcg_gear/src/optimize.rs:895-974`；`crates/jpcg_compute/src/lib.rs:378-389`。

当前是取一批 → CPU合成/时间轴 → GPU提交并阻塞等回读 → CPU归并 → 下一批。硬件10秒100次采样，两张R9700平均busy约49.8%/48.5%，47次同时忙碌，其余大量时间仅一张忙；设备实际绑定正确。

应使用有界生产消费队列及双缓冲，让CPU准备下一批时GPU处理当前批，并记录每阶段耗时。当前没有一次搜索的多卡分片；此前两张卡跑的是重复全空间对拍任务，已按用户要求停止并发，改为CPU后单卡串行测试。

### 3. 每批大量分配/复制/传输

- JointSearch每个节点 clone 两个套装计数Vec，装备已选完后仍在每个装饰节点重新计算套装加速奖励。可以冻结装备状态/奖励，再枚举装饰，减少小堆分配。
- 每个候选 decode_loadout 克隆字符串/映射，compose再线性查12件装备与装饰，最后再克隆完整Loadout。可预索引模板，并把数值合成与最终结果物化分开。
- GPU每个候选都填满64事件，实际短轴较短时浪费传输；每批新建dice/counts/hp/output/staging/uniform缓冲区，再同步map读回。
- shader每工作组256次全局atomicAdd争用同一个计数，并有末尾屏障；可先workgroup归约再一次全局写入。
- 可以复用缓冲区、按实际事件数布局、减少原子争用，但必须保留HP逐路径状态、事件顺序、f32运算和共同随机数序列。

### 4. Pareto全量串行维护与可观测性

- 主线程对每个候选线性扫描Pareto，插入时再扫描一次；生存维度相同/评分重复时可先分组，并做批内归并。
- 原始空间visited含大块剪枝，不随MC剩余工作量线性增长，前缀长时间显示0%会误导；应分别报告覆盖空间、待评分/已完成评分、实际MC次数、缓存命中及阶段耗时。
- 缺少检查点和恢复机制让小时级任务的中断成本很高。

## 已排除或需要明确的语义边界

- Timeline 的MC显式规定测量窗口开始满血重置，`full_hp`使用max_hp，与批量mc_input一致；不能仅因它未用current_hp就认定为本次批量回归bug。旧Combo的残血起步语义不同。
- allow_upgraded且无上限时只搜索升级档是当前明确实现的政策，不是“基础+升级所有档位”。基线仍可能被加入结果，而不检查其是否在裁剪后的候选列表内；应统一这个边界。
- 一次固定seed的50k MC全枚举，保证的是该有限样本评分下的最优，不是真实概率的数学最优。后端一致性、搜索完整性、统计精度需分别说明。
- 值集/技能/职业规则按请求冻结的方向正确；本次提前剪枝已做原始穷举与独立计数核对，没有在所核对的本门派空间发现漏解证据。
